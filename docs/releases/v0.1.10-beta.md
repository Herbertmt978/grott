# Grott 0.1.10-beta

This beta focuses on reliable forwarding, safer containers, and a release process that is easier to trust. No layout field definitions, data offsets, Home Assistant entity mappings, or XML-related source code were changed.

## Fixed inverter-family layout selection

- **What was the problem?** Some protocol-06 SPH and TL3 records could have their inverter-family suffix appended twice, producing an invalid layout name such as `...SPHSPH`.
- **What did we do?** Made the established layout selector the single owner of the family suffix and added regression coverage for SPH, null-padded SPH, TL3, generic fallback, strict-family mode, and smart-meter handling.
- **Why was it a problem?** A valid record could reach Grott but fail local publication because the duplicated layout name did not exist.
- **Benefit to users:** Affected SPH and TL3 records select the intended existing layout without changing its fields or decoded offsets.

## More reliable forwarding

- **What was the problem?** TCP can split one Growatt message across several reads or combine several messages into one, while a slow upstream connection could delay other sessions. A valid message could also be discarded when a malformed message followed it in the same read.
- **What did we do?** Added bounded frame reconstruction for protocols 02, 05, and 06, complete socket writes, background connection attempts, per-session failure isolation, and deterministic shutdown handling. Completed messages are now forwarded in order before a later malformed message closes only that connection.
- **Why was it a problem?** Normal network timing could otherwise cause incomplete or combined local processing, lose a valid message because of the next message, introduce delays, or disrupt an unrelated healthy logger.
- **Benefit to users:** Valid records retain byte-for-byte forwarding order, including immediately before a bad record, healthy sessions keep moving, and the proxy recovers more cleanly from slow or broken connections.

A record that fails Grott's CRC validation is still forwarded byte-for-byte when the existing command-block policy allows it, but it is skipped for local decoding and publication. This keeps the Growatt/ShinePhone path available without treating corrupt data as trustworthy telemetry.

## Parsing compatibility is protected

- **What was the problem?** Reliability work around the proxy could accidentally change a selected layout, decoded value, MQTT payload, or Home Assistant hand-off without an obvious crash.
- **What did we do?** Added a pseudonymised real protocol-06 fixture that locks framing at every split point, coalesced messages, the selected layout, all normalised values, the MQTT topic and payload, and the exact data handed to the Home Assistant extension.
- **Why was it a problem?** A change can look technically successful while subtly altering the solar values users rely on.
- **Benefit to users:** Future changes have a permanent regression guard around the established protocol-06 output contract while the surrounding reliability code can continue to improve.

## Safer configuration and Home Assistant operation

- **What was the problem?** Legacy mapping settings were parsed too permissively, environment overrides were not always validated as the final effective value, verbose logs could reveal configuration values, and the add-on could configure two MQTT publication paths. When the options file or `ha_plugin` setting was absent, its intended enabled-by-default value was written in a form the launcher did not recognise.
- **What did we do?** Replaced executable-style mapping parsing with JSON plus a safe legacy literal fallback, validated final environment-over-INI mapping, host, port, offset, and Influx settings, preserved IP, DNS, Docker service-name, and HTTP(S) URL support, redacted sensitive values, serialised extension options as JSON, normalised boolean add-on settings, and disabled native MQTT when the bundled Home Assistant extension is active.
- **Why was it a problem?** Bad settings could fail late, expose more detail than necessary, make Home Assistant behaviour harder to diagnose, or silently leave the default Home Assistant publishing path disabled on an incomplete first-run configuration.
- **Benefit to users:** Startup is safer, errors are clearer, supported legacy host and mapping formats still work, and the Home Assistant publishing path behaves consistently whether `ha_plugin` is explicitly enabled or left at its default. Grott's older native MQTT publisher remains off whenever the bundled extension is active, so there is one predictable publication path.

Optional Influx write failures are also contained so they do not prevent the Home Assistant extension from processing the same valid record.

## Hardened and reproducible containers

- **What was the problem?** The standard image and Home Assistant add-on could be built from different source paths, dependencies were not fully locked, and Grott ran with more privilege than it needs.
- **What did we do?** Both images now build from the same verified checkout with hash-locked Python dependencies and a digest-pinned base. The packaged images also keep the bundled external layout JSON files that Grott auto-loads from its working directory. Grott runs as UID `10001`, both images support read-only roots and include passive health and artifact checks, and the supplied Compose profile drops all Linux capabilities.
- **Why was it a problem?** Source drift made test results less meaningful, dependency drift made builds harder to reproduce, and unnecessary privilege increased the impact of a container problem.
- **Benefit to users:** Docker and Home Assistant installations use consistent source, retain compatibility with shipped external layouts, have safer defaults, report meaningful health, and are checked for amd64, arm64, arm/v7, and 386.

## A release process users can trust

- **What was the problem?** The previous tag-driven workflow could publish too automatically, build the two images through different source paths, promote final tags before every check finished, and rely on generated release notes.
- **What did we do?** Prepared a release workflow that starts only when the maintainer runs it. It is tied to an annotated tag and exact source commit. Before publishing anything, it checks that the default branch still points to that commit, the exact hosted `test` CI run passed, changes still require a pull request, the protected branch-only release environment exists, and an active `v*` tag ruleset protects release tags. Approving reviews and an independent environment reviewer are not required for this solo-maintainer project. Immediately before starting the workflow, the maintainer records the branch and tag bypass actors, confirms administrators cannot bypass the configured release-environment protection rules, and confirms `test` comes from the intended GitHub Actions integration. GitHub's read-only API cannot see all of those UI-only settings, so the maintainer does not start the release unless the manual check matches the required state. The workflow checks the controls it can read, then checks the live repository state again before package login, final image promotion, and prerelease creation. A default-branch rename also stops the release. It then builds both images from that exact commit, checks and scans all four platforms before attaching final tags, publishes verified image digests, and uses these committed notes.
- **Why was it a problem?** A release is only useful when users can understand it and maintainers can prove the published images match the code that passed testing.
- **Benefit to users:** Updates are easier to assess, artifacts are traceable, retries fail closed on mismatches, and publication stops when the required CI, branch, environment, or tag controls are missing. The process remains practical for a one-person project without removing the checks that protect users. This does leave one clear risk: if the sole maintainer account is compromised, that account can authorize a release. Strong two-factor authentication, preferably passkeys or hardware security keys, and minimal release credentials reduce that risk.

## Before upgrading

- Keep a copy of your working configuration and a verified Home Assistant backup.
- Docker bind-mounted configuration must be readable by container UID `10001`.
- The Home Assistant add-on and packaged Docker profiles support proxy mode only. If you currently use `server` or `sniff`, do not upgrade either packaged image; keep your current installation until a separate migration has been documented and tested.
- After starting, confirm `grott_last_push`, representative sensors, and ShinePhone all continue to update before removing your rollback copy.
