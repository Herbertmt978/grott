## Home Assistant discovery defaults

**What was the problem?** Issue #6 and testing of `v0.1.10-beta` showed that the default Home Assistant discovery map exposed far more entities than the verified `v0.1.9-beta` standard-Docker setup. Some of those additions also produced Home Assistant unit and statistics repair warnings.

**What did we do?** The exact `v0_1_9_standard` profile is now the default for supported generic and MOD packets. It exposes the verified 32 entities. The `all` option remains an opt-in MOD all map with 170 layout entities plus `grott_last_push`, for 171 discovered entities; generic `T06NNNNX` remains at 32 because it has no extra distinct diagnostics.

**Why was it a problem?** An upgrade must not silently replace a known everyday sensor set with a large diagnostic map or create unit-history conflicts in Home Assistant.

**Benefit to users:** Normal installations retain the familiar 32-entity view, while operators who genuinely need the complete MOD diagnostics can select `all` explicitly.

## Layout and complete state correctness

**What was the problem?** A sparse example `T06NNNNX` JSON could override Grott's verified built-in 31-field layout inside packaged containers. It omitted fields, changed signed power parsing, and moved the IPM temperature offset.

**What did we do?** The conflicting example is excluded from packaged images, and the final-image validator checks every verified generic key, offset, length, type, and divider. The Home Assistant profile filters discovery only: complete normalized state data still contains every decoded raw packet value plus `grott_last_push`. Existing parsing, proxy forwarding, and XML configuration inputs remain separate from entity selection.

**Why was it a problem?** Advertising an entity without backing state, or decoding it from the wrong offset or numeric type, can create plausible but incorrect telemetry.

**Benefit to users:** The 32 default entities are backed by the same generic layout contract captured from the immutable `v0.1.9-beta` runtime, with MOD aliases mapped to their matching meanings.

## Automatic retained discovery cleanup

**What was the problem?** Old retained discovery configs can leave unwanted entities behind after a profile change, while broad MQTT deletion could remove another device or integration.

**What did we do?** The candidate publishes desired retained configs at QoS 1 before same-device tombstones, then reconciles the known generic/MOD lineage only. An omitted option selects `v0_1_9_standard`, so cleanup starts on the next live packet after upgrade. A failed cleanup batch does not suppress state; the exact in-memory batch is retained and retried across later mixed-layout packets. After a process restart, cleanup is recomputed from the known topic universe and converges to the same retained set.

**Why was it a problem?** The broker must converge to 32 default topics regardless of whether the first packet is generic, MOD, partial, or follows an earlier 171-topic MOD run or 205-topic `includeall=True` run.

**Benefit to users:** Retained discovery cleanup is deterministic and device-scoped. Image rollback does not restore removed discovery, entity-registry customization, statistics metadata, or Home Assistant Repairs, so UAT requires a verified Home Assistant and retained MQTT backup before the first candidate packet.

## Changes carried forward from v0.1.10-beta

**What was the problem?** `v0.1.9-beta` is the latest supported baseline, so a later corrective candidate must also account for the substantial proxy, configuration, container, and release-process work first tested in `v0.1.10-beta`.

**What did we do?** The candidate carries forward TCP frame reassembly for split and coalesced protocol traffic, partial-write handling, deterministic socket shutdown, and the rule to forward non-blocked raw traffic before optional local processing. It retains CRC publication guards, contained Influx failures, JSON plus safe literal configuration parsing, secret redaction, source-identical non-root containers, read-only and passive-health checks, exact-source annotated tags, four-platform artifact validation, vulnerability scanning, and protected release controls across the release process.

**Why was it a problem?** Omitting those changes from the cumulative notes would make the upgrade surface look smaller than it is and hide the behavior that still needs regression testing.

**Benefit to users:** Testing and any future release decision cover the complete difference from the supported `v0.1.9-beta` baseline rather than only the new Home Assistant profile.

## Release metadata and availability

**What was the problem?** Candidate metadata must use one version across the add-on, Compose profile, documentation, changelog, release runbook, and curated notes without claiming that preparation equals supported publication.

**What did we do?** Prepared the `0.1.11-beta` / `v0.1.11-beta` metadata set while keeping `v0.1.9-beta` documented as the latest supported release and `v0.1.10-beta` as prerelease testing. The release workflow may promote image tags before GitHub release creation, so only the Releases page declares supported availability.

**Why was it a problem?** Mismatched metadata or an overconfident availability statement can lead an operator to pull an unapproved image or follow instructions for a different source SHA.

**Benefit to users:** The candidate identity stays consistent while the support boundary remains unambiguous during testing and release recovery.

## Upgrade, UAT, and rollback

**What was the problem?** Entity-map changes interact with retained MQTT, the Home Assistant entity registry, dashboards, long-term statistics, and the Home Assistant Repairs system; reverting only a container image cannot restore all of that state.

**What did we do?** UAT requires a verified Home Assistant backup plus retained MQTT coverage, exact checks for 32 default entities and 171 MOD `all` entities, alias-value checks, full state-key parity, a restart, forwarding and ShinePhone freshness, and a before/after Home Assistant Repairs comparison. Any new unit, device-class, or statistics repair is a failure. Rollback restores the recorded Home Assistant and broker state as well as the previous image and configuration.

**Why was it a problem?** A proxy can appear healthy while Home Assistant records changed units or statistics metadata that surfaces only later as repair warnings.

**Benefit to users:** A future release cannot pass merely because packets arrive; it must also preserve the practical Home Assistant experience and prove that recovery returns the original state.

## Container support boundary

**What was the problem?** Packaged profiles can be mistaken for a general migration path across Grott operating modes.

**What did we do?** The packaged Docker profiles support proxy mode only. For an unsupported `server` or `sniff` deployment, do not upgrade either packaged image. The containers continue to use the established non-root profile.

**Why was it a problem?** A mode mismatch can change networking and listener behavior in ways this candidate does not qualify.

**Benefit to users:** Testing stays on the known proxy path and does not silently become an unsupported deployment migration.
