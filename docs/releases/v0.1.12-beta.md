The GitHub Releases page is the supported-availability authority. This file describes an unpublished local UAT candidate; a source branch, local image, tag, or partially promoted image does not make it supported.

## External layout packaging

**What was the problem?** The `v0.1.11-beta` containers copied every JSON file from `examples/Record Layout` into `/app`. Grott auto-loads loader-visible `T*.json` and `t*.json` files from that directory, so packaged example layouts could override built-in layouts. One confirmed example would display SPH battery SOC 64 as 0.64. MIN signed values and field names, TL3 included fields, and T060120 offsets or inclusion rules could also change.

**What did we do?** Both containers now use the same reviewed three-file allowlist: `T06NNNNXMOD.json`, `t060103xmax3.json`, and `T06221b.json`. Bulk example-directory copies are rejected.

**Why was it a problem?** A syntactically valid example can still decode a packet differently from the maintained built-in definition and publish plausible but incorrect Home Assistant data.

**Benefit to users:** Packaged examples no longer replace the built-in SPH, MIN, TL3, or T060120 contracts merely because the container starts in `/app`.

## Final-image layout contract

**What was the problem?** Checking only filenames and top-level layout keys would still allow an approved file's divider, signedness, offset, or inclusion flags to drift.

**What did we do?** The final-image validator now requires the exact three filenames, exact layout-key ownership, reviewed semantic JSON digests, no built-in overrides, no duplicate external keys, and no unexpected loader-visible files. It also rejects malformed JSON and disguised names such as `t_layout.json.backup`, matching Grott's actual loader predicate. Static release and add-on validators forbid Dockerfile `ADD`, broad context re-includes, bulk layout copies, and unreviewed layout references.

**Why was it a problem?** A changed field definition can silently alter values without changing the external filename or record identifier.

**Benefit to users:** Source review and final-container validation independently fail closed if layout packaging or approved semantics drift.

## Hardware validation boundary

**What was the problem?** The owner has two MOD inverters, so a live test cannot honestly prove every supported record family on real equipment.

**What did we do?** MOD behavior receives a 24-hour live VM soak with both devices, ShinePhone forwarding, Home Assistant telemetry, restart, retained discovery, and Repairs checks. SPH, MIN, TL3, T060120, and generic layout preservation are fixture/container tested, not real-hardware tested.

**Why was it a problem?** Treating fixture evidence as hardware evidence would overstate confidence and could hide family-specific datalogger behavior.

**Benefit to users:** The release evidence says exactly what was exercised, while the unavailable families still have deterministic regression protection for the bug being fixed.

## Home Assistant behavior carried forward

**What was the problem?** Issue #6 showed that `v0.1.10-beta` could expose too many entities and create unit or statistics repairs compared with the supported `v0.1.9-beta` baseline.

**What did we do?** The `v0_1_9_standard` profile remains the default 32 entities for supported generic and MOD packets. The broader MOD map remains opt-in. An omitted option selects the standard profile, and retained discovery cleanup starts on the next live packet while complete normalized state data remains available internally.

**Why was it a problem?** A packaging correction must not reintroduce entity churn, suppress raw packet values, or disturb deterministic retained discovery cleanup.

**Benefit to users:** The everyday Home Assistant sensor set and cleanup behavior stay the same as the working `v0.1.11-beta` deployment.

## Changes carried forward from v0.1.11-beta

**What was the problem?** This candidate is cumulative from the supported `v0.1.9-beta` baseline, so describing only the packaging correction would hide the proxy, configuration, Home Assistant, container, and release-process behavior still under test.

**What did we do?** The candidate retains TCP frame reassembly, partial-write handling, deterministic socket shutdown, forwarding before optional local processing, CRC publication guards, and contained Influx failures. It retains JSON plus safe literal configuration parsing, XML configuration compatibility, secret redaction, source-identical non-root containers, read-only filesystem support, passive health checks, exact-source annotated tags, and four-platform validation.

**Why was it a problem?** Operators need the full upgrade surface, not only the newest diff, when deciding whether to test a beta.

**Benefit to users:** The 24-hour soak and later hosted CI cover the complete candidate behavior rather than an isolated Dockerfile change.

## Upgrade, rollback, and availability

**What was the problem?** Home Assistant entity history, retained MQTT discovery, dashboards, statistics metadata, and Home Assistant Repairs are not restored by changing only a container image.

**What did we do?** UAT requires the verified **Grott pre-update rollback** backup, retained MQTT coverage, exact `v0.1.11-beta` image evidence, one listener on TCP `5279`, live values from both MOD devices, ShinePhone freshness, restart recovery, and before/after Repairs checks. Image rollback does not restore registry or broker state. No GitHub push occurs until the owner accepts the completed 24-hour soak.

**Why was it a problem?** A healthy proxy process can coexist with stale discovery or Home Assistant metadata damage that appears only after packets arrive.

**Benefit to users:** The candidate has a concrete recovery point and cannot advance merely because it starts successfully.

## Container support boundary

**What was the problem?** Packaged profiles can be mistaken for a general migration path across every Grott operating mode.

**What did we do?** The packaged Docker profiles support proxy mode only. If an installation uses `server` or `sniff`, do not upgrade either packaged image as part of this beta test.

**Why was it a problem?** Those modes have different networking and privilege needs that this candidate does not qualify.

**Benefit to users:** The published support statement stays within the configuration actually tested by the release process.
