## Stable promotion

**What was the problem?** The immutable `v0.1.12-beta` corrected external-layout packaging, but it remained a prerelease and therefore could not become the repository's Latest release.

**What did we do?** Promote the reviewed beta behavior to the stable channel without adding another parser, layout, container, or entity-map behavior change. The protected workflow will mark the non-prerelease GitHub release Latest only after the stable release gates pass.

**Why was it a problem?** Leaving the corrected build only on the beta channel would keep an older release marked Latest even after the corrected candidate passed its required checks.

**Benefit to users:** Operators can select a stable, Latest release with the same reviewed layout allowlist and Home Assistant behavior already exercised in the immutable beta.

## External layout packaging

**What was the problem?** The `v0.1.11-beta` containers copied every JSON file from `examples/Record Layout` into `/app`. Grott auto-loads loader-visible `T*.json` and `t*.json` files from that directory, so packaged example layouts could override built-in layouts. One confirmed example would display SPH battery SOC 64 as 0.64. MIN signed values and field names, TL3 included fields, and T060120 offsets or inclusion rules could also change.

**What did we do?** Both containers use the same reviewed three-file allowlist: `T06NNNNXMOD.json`, `t060103xmax3.json`, and `T06221b.json`. Bulk example-directory copies are rejected.

**Why was it a problem?** A syntactically valid example can still decode a packet differently from the maintained built-in definition and publish plausible but incorrect Home Assistant data.

**Benefit to users:** Packaged examples no longer replace the built-in SPH, MIN, TL3, or T060120 contracts merely because the container starts in `/app`.

## Final-image layout contract

**What was the problem?** Checking only filenames and top-level layout keys would still allow an approved file's divider, signedness, offset, or inclusion flags to drift.

**What did we do?** The final-image validator requires the exact three filenames, exact layout-key ownership, reviewed semantic JSON digests, no built-in overrides, no duplicate external keys, and no unexpected loader-visible files. It also rejects malformed JSON and disguised names such as `t_layout.json.backup`, matching Grott's actual loader predicate. Static release and add-on validators forbid Dockerfile `ADD`, broad context re-includes, bulk layout copies, and unreviewed layout references.

**Why was it a problem?** A changed field definition can silently alter values without changing the external filename or record identifier.

**Benefit to users:** Source review and final-container validation independently fail closed if layout packaging or approved semantics drift.

## Hardware validation boundary

**What was the problem?** The owner has two MOD inverters, so a live test cannot honestly prove every supported record family on real equipment.

**What did we do?** MOD behavior received live VM UAT with both devices, Home Assistant telemetry, a restart, retained discovery, and error checks. On 2026-07-18, after 164 successful state publications across both MOD devices, retained `[32, 32]` discovery, a healthy exact candidate, and zero runtime errors, the owner explicitly waived the remaining planned 24-hour observation window. SPH, MIN, TL3, T060120, and generic layout preservation are fixture/container tested, not real-hardware tested. ShinePhone freshness and Home Assistant Repairs remain operator acceptance checks.

**Why was it a problem?** Treating fixture evidence as hardware evidence would overstate confidence and could hide family-specific datalogger behavior.

**Benefit to users:** The release evidence says exactly what was exercised, while the unavailable families still have deterministic regression protection for the bug being fixed. The Home Assistant add-on remains experimental because its live hardware coverage is limited to the two MOD inverters; stable describes the release channel, not universal real-hardware qualification.

## Home Assistant behavior carried forward

**What was the problem?** Issue #6 showed that `v0.1.10-beta` could expose too many entities and create unit or statistics repairs compared with the supported `v0.1.9-beta` baseline.

**What did we do?** The `v0_1_9_standard` profile remains the default 32 entities for supported generic and MOD packets. The broader MOD map remains opt-in. An omitted option selects the standard profile, and retained discovery cleanup starts on the next live packet while complete normalized state data remains available internally.

**Why was it a problem?** A packaging correction must not reintroduce entity churn, suppress raw packet values, or disturb deterministic retained discovery cleanup.

**Benefit to users:** The everyday Home Assistant sensor set and cleanup behavior stay the same as the working `v0.1.11-beta` and immutable `v0.1.12-beta` deployments.

## Changes carried forward from v0.1.11-beta

**What was the problem?** This release is cumulative from the supported `v0.1.9-beta` baseline, so describing only the packaging correction would hide the proxy, configuration, Home Assistant, container, and release-process behavior included in the stable release.

**What did we do?** The release retains TCP frame reassembly, partial-write handling, deterministic socket shutdown, forwarding before optional local processing, CRC publication guards, and contained Influx failures. It retains JSON plus safe literal configuration parsing, XML configuration compatibility, secret redaction, source-identical non-root containers, read-only filesystem support, passive health checks, exact-source annotated tags, and four-platform validation.

**Why was it a problem?** Operators need the full upgrade surface, not only the newest diff, when deciding whether to install the stable release.

**Benefit to users:** Live MOD UAT and hosted CI cover the complete cumulative behavior rather than an isolated Dockerfile change, while the limited hardware boundary remains explicit.

## Upgrade, rollback, and availability

**What was the problem?** Home Assistant entity history, retained MQTT discovery, dashboards, statistics metadata, and Home Assistant Repairs are not restored by changing only a container image.

**What did we do?** Upgrade acceptance requires the verified **Grott pre-update rollback** backup, retained MQTT coverage, one listener on TCP `5279`, live values from both MOD devices, advancing `grott_last_push`, ShinePhone freshness, restart recovery, and before/after Repairs checks. Image rollback does not restore registry or broker state. Every PR, hosted-CI, protected-branch, tag, environment, image-validation, and publication gate still applies.

The immutable `v0.1.12-beta` images are the exact container rollback evidence for this stable promotion:

- Docker runtime: `ghcr.io/herbertmt978/grott@sha256:066d806774a147bc4c448761d026eb831cdcfa29bc32ef3a1c361a36a2ea361a`
- Home Assistant add-on: `ghcr.io/herbertmt978/grott-ha-docker@sha256:410f2b2e4dfe810aa1d9d8b8591eaae0852ae9f61486d78f663cd6a95c2ab6f1`

**Why was it a problem?** A healthy proxy process can coexist with stale discovery or Home Assistant metadata damage that appears only after packets arrive.

**Benefit to users:** The stable release has a concrete recovery point and cannot advance merely because it starts successfully. Docker rollback pins the runtime digest and restores the previous configuration. Home Assistant rollback stops the candidate and restores the verified full backup and retained MQTT state; the add-on digest identifies the prior artifact but does not replace that recovery path.

## Container support boundary

**What was the problem?** Packaged profiles can be mistaken for a general migration path across every Grott operating mode.

**What did we do?** The packaged Docker profiles support proxy mode only. If an installation uses `server` or `sniff`, do not upgrade either packaged image as part of this release.

**Why was it a problem?** Those modes have different networking and privilege needs that this release does not qualify.

**Benefit to users:** The published support statement stays within the configuration actually tested by the release process.
